# Agent Note:PTY 通道应答光标位置查询

Status: implemented

[English](2026-08-20-pty-cursor-position-responder.md) | 中文

## 问题

node-pty 终端不是终端模拟器:主侧没有任何组件应答设备状态报告查询。POSIX 控制台栈会在等待应答时阻塞交互式启动——pwsh 在控制台初始化期间发出 `ESC[6n`,若收不到 `ESC[row;colR` 应答,就永远不会渲染第一个提示符、不会执行已提交的输入,回卷缓冲里只有内核对超前写入内容的回显。Windows 上 ConPTY 在内部处理该查询,因此面向 Windows 编写并验证的交互式 pwsh 路径(终端会话与持久 pwsh 工具)在 rc.8 套件第一次跑 darwin CI 时全部卡死:每个 send 都以静默推断收尾,viewport 为空。

## 决策

`LocalTerminalHandle` 扫描 PTY 输出流中的 `ESC[6n`,并向 PTY 输入应答固定的光标位置报告 `ESC[1;1R`。一个有界缓冲补全跨数据块拆分的查询。该应答是把终端模拟器行为移入主侧;位置值固定,因为通道不做屏幕渲染,也不存在真实位置的消费者。应答器在 Windows 上保持休眠。pwsh 终端方言同时把 `TERM` 从 `dumb` 改为 `xterm-256color`,使 PSReadLine 的交互式读取器正常启动;流式 sanitizer 本就丢弃转义序列,多出的 VT 输出不改变下游行为。

## 考虑过的替代方案

**等待第一个原生提示符再写入引导行。** 卡死发生在任何输出之前,不存在可等待的信号,且两种方言的就绪语义会产生分叉。

**以非交互模式运行 pwsh。** 非交互模式下提示符不渲染,`stdin_read` 就绪检测与提示文本检测依赖的 OSC `133;D;` 标记随之消失。

**为应答跟踪真实光标位置。** 通道不做屏幕建模;对发起查询的控制台栈而言,构造的位置与真实位置不可区分,它只需要格式良好的报告。

## 结果

交互式 pwsh 会话在 POSIX 上完成初始化并渲染其提示函数,终端会话恢复基于标记的 `stdin_read` 就绪,持久 pwsh 工具恢复基于标记的输出提取。bash 方言与 Windows 行为不变。测试固定了应答器对完整、重复、拆分查询的行为,以及对其他 DSR 码的拒绝。
