# Agent Note: 桌面端健康探测完成运行时启动令牌握手

Status: implemented

[English](2026-09-02-desktop-launch-token-health-probe.md) | 中文

## 问题

Harness 0.1.2-alpha.3 起的运行时不再直接返回 Web 壳，而是对声明的 `dsh web` URL 返回 303 重定向到 `/` 并下发会话 cookie。桌面宿主的启动健康检查以 `redirect: 'error'` 请求该 URL 并要求立即得到携带 `__DSH_BOOT__` 的 200 响应，因此这类运行时的每次启动都会超过启动期限。`startSelectedRuntime` 重试候选一次后清除 pending 选择，并在旧运行时上无声继续：用户接受了 Harness 更新、重启之后仍在运行旧版本，日志和对话框中没有任何记录。

## 决策

`runtime-process.ts` 的健康探测现在跟随该握手：对 `location: /` 的 303 响应，取第一个 `Set-Cookie` 键值对重新请求去掉查询串的 URL，只有携带 `__DSH_BOOT__` 的已认证 200 才证明壳就绪。直接返回标记的响应仍然通过，早于该机制的运行时不受影响。`startSelectedRuntime` 把每次候选启动失败记入桌面日志，两次失败被拒绝的候选会在下一次启动时提示一次，包含回退版本和原因。这与运行时构建已使用的认证冒烟探测一致，release workflow 的打包冒烟测试现在也通过同一路径启动种子运行时。

## 考虑过的替代方案

**让运行时对回环监听免握手直接返回壳。** 拒绝：启动令牌的作用正是保证 Web 壳不被未认证访问；为桌面端削弱它会重新暴露其他所有 `dsh web` 使用方。

**把任何可达的 HTTP 响应视为健康，让窗口加载去暴露失败。** 拒绝：健康标记证明的是真实 Web 壳而非残缺或错误的服务器；放弃它会把候选失败挪出两次尝试的拒绝路径。

**只写日志、不加启动提示。** 拒绝：用户不会读日志，而被报告的缺陷正是这种看起来像更新失败的静默回退。

## 后果

桌面 1.5.6-preview.1 及以后版本可以激活 0.1.2-alpha.3+ 的运行时更新；更早的桌面宿主仍会静默回退，必须先完成壳更新。探测只接受携带 cookie 键值对的精确 303-到-`/` 形态，其他重定向或状态码都会继续重试直到启动期限。被拒绝的候选在 `logs/runtime.log` 中留有记录，一次性的启动提示会给出候选、回退版本和首次失败原因。
