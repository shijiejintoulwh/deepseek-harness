# Agent Note: Windows 桌面壳应用内更新

Status: implemented

[English](2026-08-21-windows-desktop-shell-updates.md) | 中文

## 问题

独立版本的 Electron 壳需要接收修复，而不应要求用户每次都自行查找并运行 `desktop-v*` 安装器。既有 Harness 更新器不能负责这个操作：它安装不可变的运行时目录、维护 `active`／`previous`／`pending` 状态，并可通过选择另一个运行时完成回滚；NSIS 则会替换壳安装目录中的文件并重新启动应用。

GitHub 通道元数据与传输安全本身不能认证社区桌面安装器。预览版和稳定版用户也需要不同的发现规则，确保实验性 release 既不会取代稳定通道，也不会让已安装的壳降级。

## 决策

Electron 主进程拥有独立于 Harness 运行时更新器和 `RuntimeStore` 的 `ShellUpdater`。壳检查、下载、错误和安装就绪状态各自维护；壳下载与运行时下载互斥，壳安装也绝不更改运行时选择或删除任何运行时版本。

已安装的壳版本会选择对应通道。稳定版只接受更高的稳定版本；预览版可以接受更高的预览版本或稳定版本。准确的 SemVer 比较会拒绝已安装版本、更旧的 release、从稳定版跨通道进入预览版以及所有自动降级。

宿主会进行静默后台检查，并在 Harness 更新命令旁提供独立的 `检查桌面端更新` 命令。发现版本本身绝不会开始下载：用户需要先确认传输，下载经过验证后还要单独确认 `重启并更新`。普通退出不会安装待处理的壳 release。

`electron-updater` 提供 Windows `NsisUpdater`、通道元数据处理、blockmap 支持与 NSIS 交接。自动下载和退出时安装均被禁用。用户确认安装后，宿主会先通过既有明确退出路径，让 Harness 进程树和日志流完全收敛，释放托盘资源，再要求 updater 重启进入按当前用户安装的 NSIS 引导式安装器。安装器会保留用户选择的安装目录。

每个桌面端 release 文件集都包含 NSIS 可执行文件、对应 blockmap、一个且仅一个通道文件（稳定版使用 `latest.yml`，预览版使用 `preview.yml`）、`desktop-update-manifest.json` 与 `desktop-update-manifest.sig`。桌面端专用 Ed25519 密钥会对清单的准确字节签名。严格清单绑定壳版本、稳定或预览通道、源码提交、安装器与 blockmap 的名称、大小、SHA-256 摘要以及发布时间。客户端会先验证签名再使用清单字段，要求所选通道与候选版本一致，并在显示重启操作前验证两个下载文件。

只有构建与打包后冒烟测试通过，受保护的发布 job 才能取得桌面端签名密钥。它会在签名和发布前检查 package 版本、`desktop-v*` 标签、prerelease 状态、通道元数据、完整文件集、安装器大小与 SHA-256。预览版 release 只写入预览通道元数据，稳定版 release 只写入稳定通道元数据。同一个标签和版本标识不可变字节，绝不以另一个摘要重新发布。

壳安装只替换 Electron 应用文件。用户数据与桌面版专用 Harness home 继续位于 `%APPDATA%\DeepSeekHarnessDesktop`；运行时版本及其原子选择状态继续位于 `%LOCALAPPDATA%\DeepSeekHarnessDesktop`。因此，下载、验证、发现或安装器失败后，当前壳和运行时状态仍然可用。

MVP 不增加自动壳回滚。下载或验证失败时继续运行当前壳，并可重试。安装器失败后会保留已经验证的安装包，供用户明确重试或手动安装；当 NSIS 可能仍持有应用文件时，程序不会尝试自行恢复这些文件。

## 验证

针对性更新器测试固定稳定版与预览版选择、禁止降级、用户确认下载、用户确认重启、禁止退出时安装、清单签名与严格字段拒绝、大小与 SHA-256 不一致、并发更新排斥以及失败行为。Workflow 测试固定版本／标签／通道一致性、机密隔离、完整桌面端产物、不可变发布与预览元数据隔离。打包冒烟测试覆盖当前安装器与更新元数据。在更高的预览版本发布前，真实安装后的预览版跨版本更新仍是明确的覆盖缺口；该 release 只有在更新过程保留自定义安装目录与两个应用数据根目录，并证明新壳可以启动后，才会被认定为可升级。

## 考虑过的替代方案

**复用 Harness 运行时更新器与回滚状态。** 拒绝，因为运行时激活选择不可变目录，壳更新则通过 NSIS 替换正在运行的 Electron 安装。共享状态会让安装器失败有机会破坏无关的运行时回滚记录。

**只信任 Electron 通道元数据与 HTTPS，不使用桌面端清单签名。** 拒绝，因为通道 YAML 只能定位文件，不能提供产品自身不可变的 release 身份。签名清单让预期通道、版本、来源、字节长度与摘要都可独立验证。

**自动下载每个发现的 release。** 拒绝，因为后台检查不应在未经同意时消耗安装器下载带宽。发现、下载与重启继续作为三个独立的用户决定。

**在普通退出时自动安装。** 拒绝，因为托盘应用可能在用户仍有活跃工作或操作系统关机时退出。只有明确的重启操作才授权完全收敛关闭与 NSIS 交接。

**向稳定版用户提供预览版 release。** 拒绝，因为预发布测试不能静默扩大稳定通道。预览版用户仍可直接进入更新的稳定版，而无需重新安装或降级。

**在 MVP 中实现壳回滚。** 拒绝，因为 NSIS 会修改运行时不可变目录模型之外的应用文件。可信的回滚需要单独打包上一个安装器并设计恢复流程；下载和验证失败无需这套机制也能安全地继续运行当前壳。

## 后果

桌面端修复可以触达已经安装的预览版和稳定版用户，而无需把壳 release 绑定到节奏更快的 Harness 运行时。用户保留对安装器带宽和重启时机的控制，既有运行时激活、候选验证与回滚行为均保持不变。

桌面端 release 发布会增加第二套签名身份和不可变清单。私钥留在仓库之外，只对受保护且不检出仓库的发布 job 可用；轮换密钥时必须同时发布内嵌替换公钥的壳版本。

NSIS blockmap 可以减少传输量，但正确性仍取决于完整下载的安装器是否符合签名后的预期摘要。缺少自动壳回滚意味着安装器失败后可能需要明确重试或手动重新安装，而 `%APPDATA%` 用户数据与 `%LOCALAPPDATA%` 运行时状态仍保持独立并可恢复。
